# Should the shared code become a library plugin?

**Short answer:** yes, that is the right end state. Split right after the rubric_ranges port
works, not before. This matches the recommendation in [`REFACTORING.md`](../REFACTORING.md)
section 10.

## Why split eventually

- **The grading method menu.** Core lists every installed `gradingform_*` plugin in the
  grading method menu (`grading_manager::available_methods()`), and a grading method can't
  be disabled. If [BTEC](https://github.com/marcusgreen/moodle-gradingform_btec) or
  [rubric_ranges](https://github.com/catalyst/moodle-gradingform_rubric_ranges) depended on
  `gradingform_matrix`, every site that installs them would offer "Matrix" to teachers. A
  library plugin (`local_` or `tool_`) never appears in that menu. This alone settles it.
- **Separate versions.** A change to the framework API shouldn't force a matrix release,
  and the reverse holds too. It also lets you mark the stable surface `@api` and keep an
  `UPGRADING.md` for the library alone.
- **Clearer ownership.** Shared strings, Behat steps, generators and contract tests sit
  under a neutral component name. Matrix becomes a small demo that no production site
  needs to install.

## Why not split today

- **The abstractions are only tested against one method.** Every class in
  `classes/local/framework/` has been shaped by matrix alone. The first port
  (rubric_ranges: per-criterion scoring, a `score` filling field) will probably change the
  API, and changing it across two plugins costs more than changing it inside one.
- **The split is cheap later.** The code already lives in its own namespace
  (`\gradingform_matrix\local\framework\`). Moving it is mostly a namespace rename plus a
  `$plugin->dependencies` line in each method.
- **Overhead during alpha.** Two plugins to install, version and keep in step while the
  code changes daily.

## Fix: importer lang strings

`definition_importer` was the only framework class tied to matrix. It threw its errors and
called `get_string()` with strings from `'gradingform_matrix'`, so a library version would
have depended on matrix's lang file.

The lang component is now a constructor argument, the same way the repositories take their
table names:

```php
new definition_importer(self::get_default_options(), 'gradingform_matrix');
```

- Every `moodle_exception` and `get_string()` call uses `$this->component`.
- The class docblock lists the strings the component must define: `importerrorjson`,
  `importerrorversion`, `importerrorstructure`, `importerrorfile`, `importerrorscore`,
  `importwherelevel` and `err_nocriteria`.
- `parse_files()`, `parse_score()` and `require_criteria()` are now instance methods
  instead of static, because they need the component.
- Callers updated: `lib.php` (`gradingform_matrix_controller::definition_importer()`) and
  `tests/local/framework/definition_importer_test.php`.

Verified: `definition_importer_test` (6/6) and `import_export_test` (6/6) pass, and phpcs
(Moodle standard) reports nothing on the changed files.

When the library is extracted, these strings can move into the library's lang file and the
default component can point there. Methods would then pass their own component only to
override the wording.
